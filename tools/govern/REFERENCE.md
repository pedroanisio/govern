## Overview and other hosts

`govern version` (or `govern --version`) prints the installed package version. Add `--json` for the name and version as JSON.

You and the owner do the work together; `govern` keeps that conversation cheap and keeps the work in files. A lane of work follows a **process** (its stages, exit conditions, checks and the owner's gates), and nothing in govern knows one kind of work: a new kind is a new process description. The money in agent work goes into four things, and the rules below remove them:
- re-reading a huge context on every call;
- polling long jobs from inside the model;
- review and fix agent cascades;
- sessions messaging each other.

A process may own a manual with the rules of its kind of work (for example how a build runs or what its steps must say). The brief names it when it does (`manual: govern manual <process>`); read it once, then work from the brief. `govern manual <process>` prints it.

*Extension: peer (and center, for the command center); `govern ext enable peer`.* For a recipient on another host, `govern task send --to NAME@PEER` uses a live static peer or mesh member and skips
local session liveness. `govern agents list` shows what you may address on every other host (`--refresh` asks them
now). To be reachable from other hosts yourself, run `govern agents register --project P [--description TEXT]`: it
publishes your own inbox as NAME@HOST, for those projects, until it expires (12 hours by default) or your session
ends. A named session registers its own name; an unnamed session may choose a free name with `--as` or use
`--ephemeral`. Names and aliases held by a live session belong only to that session. `--alias NAME` adds names you also answer to; `--ephemeral` registers a
generated short-lived name instead (read its inbox with `govern task inbox --as NAME`, NAME being the generated name). Names and aliases are
unique on a host and held by the session that registered them. Registrations whose name or alias becomes a runner
or profile stop being advertised and grant no run; `govern agents unregister` withdraws yours. A reply to
a message you sent to another host reaches you even when that host is not granted to address you. The receiving host decides write access, profile, lane, spend estimate and files: do not pass `--write`,
`--profile`, `--lane`, `--estimate-usd` or `--file`, and do not use `auto@PEER`. `govern peer push` relays one pass;
`govern task dispatch --loop` relays after each local pass. Sessions on PEER are not woken by the queue. Unverified
output never leaves the host. `govern peer list` shows each peer's grants, open outbound messages and last relay
error. `govern peer id`, `govern peer add`, `govern peer revoke`, `govern peer serve`, `govern mesh create`,
`govern mesh invite`, `govern mesh join`, `govern mesh policy` and `govern mesh revoke` are the owner's setup steps:
those that grant runs work only from the owner's own terminal, and you never run them. `govern mesh status` and a
plain `govern mesh sync` are safe to run. `govern center show` prints the operator's command center: every federated
host's health, alerts, agents, spend and latest messages; `govern center serve` shows it in a browser for the owner (the address and its token are kept in the private state and survive restarts: `govern center url` prints them; `--new-token` rotates; the agents list shows the folder each agent works in), with a Projects view (every host's lanes: stage, status, gates, last check) and a Processes view (live BPMN of any process, from any host, and of any lane); `govern bpmn <process|lane>` draws the same diagram in a terminal session (SVG, scene or PNG). All of it is read-only. See [PEERS.md](PEERS.md).

## Start

The owner's one screen is `govern desk`: every lane, their inbox, the queue and today's tokens. One session works one lane; the other lanes wait in their files, not in open chat tabs. A session that starts in a lane's folder (or with `GOVERN_LANE=<slug>`) already has its work segment: the `govern hook session-start` hook (`govern install-skill` prints the line to add) opens it on the lane's current stage.

*Extension: remote; `govern ext enable remote`.* The owner can also follow the lanes from a phone: `govern remote serve` serves the desk, each lane and today's telemetry to paired devices (the Android app in `android/`), and a paired device approves gates and acknowledges alerts with a signature the owner confirms on the phone (REMOTE.md). `govern remote pair` makes the one-time pairing code and is refused inside an agent session: never pair a device, and never ask the owner for a code. A phone can also ask to pair: `govern remote link` prints the link it scans, `govern remote requests` lists open requests with their 6-digit comparison codes, and `govern remote confirm <id> --code NNNNNN` (or `govern remote refuse <id>`) answers one; if no lanes were requested, confirm requires `--lane SLUG` (repeatable) or `--all`. These, too, are the owner's alone. `govern remote devices` lists paired devices and `govern remote revoke <id>` cuts one off; both are the owner's. An approval whose source is `device` is the owner's own words, as valid as one from their terminal.

Add review evidence with `govern artifact add <slug> <file> [--name N] [--title T] [--caption C]`; it copies private bytes into the lane and records their SHA-256 and version. `govern artifact list <slug>` prints metadata and reviews of the current digest. Replacing bytes invalidates reviews of older bytes. Paired phones can read artifacts, sessions and job logs through the remote API.

1. `govern status` lists the lanes. If the lane is not there, run `govern new <slug> --process <name> --title "…"` (`govern process list` shows the processes; a process with kinds needs `--kind`, and `--lang` sets the language; `--parent <lane>` links a lane to another; `--pin` freezes the process definition into the lane even when the process declares no revision). Without `--process`, `--kind long`, `short` or `ops` picks the process: `ops` the ops process, the others video. The slug is its folder under the workspace's projects folder.
2. `govern work <slug> <stage>`. The stages are the process's own (`govern process show <name>`). This opens a measured work segment and prints the **brief**:
   - stage and exit condition;
   - approvals;
   - named files;
   - commands;
   - last jobs;
   - recent decisions.

   The segment's `work` ledger entry carries `skillSha`, the sha256 of this manual (tools/govern/SKILL.md) when the segment opened, so a segment can be matched to the rules it ran under; `--open` records it too.

   `govern brief <slug>` prints the brief again without opening a segment. Work from the brief; do not read the workspace's long process documents in full. The brief carries the exit condition, and `govern ask` carries the rules each step needs.
3. If the lane's commands or files are not named yet, name them once (a process can do this at `govern new`, from its `setup`):
   - `govern cmd <slug> build -- {python} build.py --preview`. Placeholders: `{python}`, `{repo}`, `{dir}`, and `{paths.NAME}` for a path the workspace's config names under `paths`.
   - `govern file <slug> report summary.json`
   - `govern file <slug> sheet "out/**/*sheet*.png"`. A glob means its newest match.

`govern help` lists every command with its flags; `govern help <command>` (or `govern <command> --help`) shows one. The command comes first, then its subcommand (`govern task send …`), then arguments and flags. A flag the command does not take, a switch given a value other than true or false, and a value flag with no value are refused (exit 2) with the command's valid flags. A value flag takes the next word as its value even when it starts with `--` (`--note "--verbose test passes"`), unless that word is itself a govern flag (`--note --bg` forgot the note); give such a value as `--flag=VALUE`. `govern manual` prints this manual and lists the processes that have their own; `govern manual <process>` prints that one; `govern install-skill [<skills dir>]` makes `<skills dir>/govern` (default: the repo's `.claude/skills`) a symbolic link to the tool's tracked folder `tools/govern`, which holds SKILL.md (the core) and REFERENCE.md; skills are tracked in git beside their tool and a `.claude/skills` entry is a link, never a copy, so an edit to SKILL.md is live at once. A link already pointing there is left alone (exit 0, already installed); a link pointing elsewhere is replaced; a real directory or file is refused (exit 1, naming it and the fix) unless `--replace` is given, which removes it and creates the link. Nothing outside `<skills dir>/govern` is touched. `govern install-skill [<skills dir>] --check` installs nothing: it exits 0 when the entry is a link resolving to the tool folder whose SKILL.md has the current sha256, and 1, naming the path, what it found (missing, a copy, a link elsewhere, a stale sha) and the fix, otherwise.

## Any process, any group of agents

govern is not tied to video. A lane follows a **process**: stages, the exit condition of each, the command that checks it, and the owner's gates.

- `govern process list` shows them; built in are `video`, `ops` and `dev` (plan → build → test → review → done); the video process carries its own manual, prompts and setup under `processes/video/`. `govern process show <name>` prints the stages, checks and gates. A workspace adds its own as JSON in its processes folder; a file with a built-in's name overrides it. A process file is parsed strictly: `version` 1, `name`, `stages` (`{name, exit?, check?, requires?: "check"}`), and optionally `description`, `kinds`, `exitFrom: "workflow"`, `gates` (`{name, stage?, needs?, message?, owner?}`; `owner` is who decides the gate, default "owner"), `manual` (the process's manual file), `prompts` (its prompts folder) and `recipes` (see Recipe jobs) and `setup` (groups of `commands` and `files` a new lane starts with, a group with `ifFile` only when that file is in the lane's folder). The paths in a process file are relative to it. An unknown key, a wrong type, a duplicate stage or gate name, a gate naming a stage or gate that does not exist, or gates that need each other stops every command with exit 4, naming the file and the JSON path (`$.stages[1].chek`). Fix the file; nothing guesses past it. A lane's govern.json is parsed the same way: only the keys govern writes, each of its type (a command is an argv array or `{argv, timeout?}` with a whole-number timeout), `slug` equal to the lane's folder, a process that exists with a kind that fits it, a `stage` and `checks` keys that are the process's stages, and timestamps in ISO form. A bad govern.json stops a command on that lane with exit 4; `govern status` and `govern desk` still list every other lane, show the bad one as a `✖` row with its file, path and message, and then exit 1. Change a lane through govern commands, not by editing the file.
- - `govern bpmn <process|lane>` draws a process as a BPMN diagram, read-only: owner, coordinator, worker-agent and stage-check lanes, stages as tasks, each check as a task with a pass/gap gateway and a dashed loop back, each gate as a user task in its owner's lane, `next` routes, splits and joins as gateways. Given a process name it adds the live state of the lanes on it (how many lanes stand at each stage, with clickable slugs in the page; pending gates; failing checks); given a lane slug it draws that lane's own process (its frozen snapshot) with its progress: stages done, current, blocked or not yet reached, each gate approved, rejected, pending or waiting with who and when, each check's last result and the first failing line. The SVG goes to stdout or `--svg FILE`; `--scene FILE` writes a scene-render scene; `--png FILE` renders it with `$SCENE_RENDER` or `scene-render` on PATH and fails plainly, writing nothing, when neither exists (`--width`/`--height`, default 3840 wide; `--static` leaves out the live state). A process name wins over a lane slug of the same name.
- `govern new <slug> --process dev --title "…"` starts a lane on that process.
- **The workspace.** govern works in the folder named by `GOVERN_REPO`, else the nearest folder at or above the current directory that holds a `.govern/` folder or a `govern.config.json`; with neither it stops and says so, and guesses no default (no `~/.govern`). **The convention:** `govern init [<dir>]` creates `.govern/` with `projects/`, `queue/`, `processes/` and a `.gitignore` for run state (`state/`, job logs; lanes and their ledgers stay tracked). It refuses a folder that already is a workspace, and a folder inside one (naming the enclosing workspace, which the new one would shadow) unless given `--nested`. In a `.govern/` workspace the lanes, queue, processes, capabilities, state (`.govern/state`) and tuning log (`.govern/tuning.jsonl`) live inside it with no config at all (`state` is govern-state beside the projects folder otherwise; below, `<state>` is that folder); an optional `.govern/config.json` takes the same keys, relative to `.govern/`, and overrides any of them. The workspace root (`{repo}`, where commands run) is the folder that holds `.govern/`. A folder holding both `.govern/` and `govern.config.json` is refused, never a silent pick; the nearest marker wins. The `govern.config.json` form names every path itself: the file (`projects` required, and `queue`, `processes`, `workflow`, `tuningLog`, `packages`, `prompts`, `paths`, `baseline`, `capabilities`, `resources`, `state`; paths relative to the file, strict like a process file) says where a lane, the queue, the processes and the tuning log live. A command that needs a key the file lacks names the file and the key. `resources` is checked as the resources list (or a path to it); a relative or trailing-slash `GOVERN_REPO` is resolved to an absolute path. `{paths.NAME}` is expanded in process commands and queue runner argv alike; `govern new` warns on stderr (and still creates the lane) for a `{paths.X}` the config lacks. With no workspace, `govern prompts` and `govern caps` list the built-in prompts and profiles only. The env overrides (`GOVERN_PROJECTS`, `GOVERN_QUEUE`, `GOVERN_PROCESSES`, `GOVERN_WORKFLOW`, `GOVERN_PROMPTS`, `GOVERN_TUNING_LOG`, `GOVERN_CAPABILITIES`, `GOVERN_RESOURCES`, `GOVERN_STATE`) win over the file. A different team or project runs govern with a config and its own processes folder, with no change to govern.
- **Exit checks.** A stage whose process names a check (dev's test stage checks `test`) is done only when that command passes: `govern cmd <slug> test -- <command>` names it once, and `govern check <slug> --set <cmd> --stage <stage>` points any other stage at a command. `govern check <slug>` runs the check now. Every `--set` goes into the ledger (from: the stage's check before it, the lane's own or the process's; to), and so does every `govern cmd` set or `--rm` (the command before and after, as govern.json stores it, and the stages whose check it is). A **swap** is flagged: a stage's existing check pointed at another command, or a command that is some stage's check redefined or removed. Setup is not: a stage with no check getting one, a command defined for the first time. The brief shows a ⚠ line for every stage with a flagged swap, whatever stage the lane is at, until the lane is finished or the owner accepts it with `govern check <slug> <stage> --accept --quote "<exactly what the owner said>"`, which clears that stage's changes made before it (a later swap is flagged again). Nothing else clears it: not the check passing (a gamed check is what passes), not moving back and forth, not leaving the stage. An acceptance is the owner's, like an approval: never infer it, and never accept for the owner. Setting a check or a command to what it already is changes nothing (no ledger entry, no ⚠); the same argv with another `--timeout` is a change. Never swap a failing check, or the command it names, for one that passes.
- **Timeouts.** A command run in the foreground (a check, `govern run` without `--bg`) gets 30 minutes unless `govern cmd <slug> <name> --timeout <seconds> -- <command>` gives it its own limit. Past it, the job's processes (as **Stopping a job** counts them) get SIGTERM, then whatever is left gets SIGKILL 3 seconds later; the job reads `timeout` and the check fails as "timed out after Ns". A foreground command stays in govern's process group, so Ctrl-C stops it together with govern. The timeout is kept by the govern that waits on the command: if that govern is killed some other way (by its pid, with no signal to its group), the command runs on with no limit and its job reads `running`; `govern kill <slug>` stops it and records its end.
- **Resources.** `govern.config.json` declares the machines, services and accounts a job may run on (`"resources": [...]` or a path to a file of them; `GOVERN_RESOURCES` names another file): `name`, `kind` (free text), `sharing` (`shared`, or `dedicated` with `to`: a lane slug or a folder like `bench/`), `price` (`free`, or `per-second`/`per-hour` with `currency` and `amount`, or `per-month` with `amount`), `allowance` (`text`, optional `maxJobs`, `maxMachines`), optional `"lock": false` (no lock at all; without it every resource, dedicated ones too, has `maxJobs` slots, default 1, and a second job waits) and optional `start`, `stop`, `list` argv lists. `govern resources` lists them; `govern resources <name>` shows one with its lock holders and the queue behind it. `govern run <slug> <cmd> --on <resource>` runs the job there, and `govern cmd <slug> <name> --resource <resource> -- ...` makes `--on` implied for that command (the resource is checked when the command is set: unknown or not allowed for the lane is refused). A command that has its own resource refuses a different `--on` unless `--override-resource` is given; the job record keeps `overrode`. A resource takes a crash-safe lock (one job at a time unless `maxJobs` says more, or `"lock": false` says none; a holder that died is reclaimed by its pid and start time), and a job over the limit waits first in, first out: foreground `run` waits in place, a `--bg` job reads `queued on <resource>` in `govern jobs`, and `govern wait` covers the wait with no model involved. A dedicated resource refuses lanes it is not dedicated to. **Benchmark jobs name a dedicated resource** (`--on <bench machine>`), so their timings are never taken beside other work. Every job records its resource (`local` when none) and its machine seconds in the ledger (the wall seconds less any wait in line); a lost job's seconds stop at its last sign of life (newest mtime of its log or slot file) and the entry says `estimated`, or `unknown` with no seconds when it left none; a `per-second` or `per-hour` resource also gives money in its currency (price as it was when the job started), and `per-month` gives seconds only. `govern usage` and `govern desk` show machine seconds and money beside tokens, per lane. Limits: `maxMachines` is enforced where machines are started (`govern slice` and `govern up --count N` are both refused above it), not by `run`; the lock is a directory lock under `<state>/locks` (set `GOVERN_STATE` to move it), not an OS flock.
- **Reaping what govern started.** A resource's `start`, `stop` and `list` argvs are run only by these commands, with no shell, in the repo folder, for `--timeout` seconds (default 120). `govern up <resource> [--lane <slug>] [--count N]` runs `start` under a fresh tag, `govern-<lane>-<job>-<6 hex>` (lowercase, so a provider can use it as a label): it is in the environment as `GOVERN_TAG` (also `GOVERN_LANE`, `GOVERN_RESOURCE`, `GOVERN_COUNT`) and replaces `{tag}`, `{count}`, `{lane}` and `{resource}` in the argv. The command must print the instance ids, one per line, and nothing else; an `up` inside a job takes the lane and job from `GOVERN_JOB_DIR`. The record (`{tag, resource, ids, lane, job, startedAt, price}`) is written to `<state>/instances/<tag>.json` before `start` runs, so a start that crashes, times out, fails or prints something that is not an id still leaves its tag (status `start-failed`), and the failure is reported with exit 1. `govern down <tag|id>` runs `stop` once per instance with `{id}` and `GOVERN_ID`; a stop that fails stays running and is reported. `govern down <tag|id> --forget` books the time without running `stop`, for a machine that is already gone. `govern reap [<resource>]` runs each `list` (only resources that have one) and expects `<id> <tag>` lines (a bare `<id>` is an untagged instance). An instance is govern's only when its tag is one recorded in `<state>/instances`; a name that merely looks like a govern tag, or any other tag, is counted as "no tag govern issued" and never touched. Of govern's, the ones still running with no live job are listed: not in use means its job is not running and its lane has no running job on that resource (a start still in progress counts as in use for 15 minutes). `reap` stops nothing without `--yes`; with it, it runs `stop` for each listed instance and ledgers a `reap`. A listing that fails, times out, prints a line outside the grammar, or prints nothing while govern started instances it has no record of stopping is reported (exit 1) and never read as "nothing to reap"; if the instances are really gone, `govern down <tag> --forget`. Every listing is written to `<state>/reap-scan.json`; `govern task dispatch --loop --reap-every <seconds>` (also on `install-service`) does the same on a timer, off by default, and never stops a machine. `govern desk` shows "N instances running with no job" when N is not zero, and a failed listing. Machine time from `up` to `down`/`reap` (per instance, wall clock) goes into the ledger with the resource's price basis and the price recorded at `up`, so `govern usage` and the desk show a stopped machine as seconds and money (a `per-month` one as seconds only); an `up` with no lane books to `<state>/ledger.jsonl`, shown on the desk as "(no lane)". Limits: money is booked when the machine is stopped, not while it runs; an instance with no lane, or whose job has been deleted, shows as orphaned; the dispatcher's listing blocks its loop for up to `--timeout` seconds; a listing that fails (for example because the service has no provider credentials) shows on the desk as a failed listing, so a reap that cannot run is visible there. A `down` or `reap` takes a per-tag lock and re-reads the record inside it; `reap --yes` re-checks before each stop and skips an instance whose resource lock is held or waited for by any job, whatever lane. Down and reap book the machine's lifetime, which is not added to job time on the same resource (totals take the larger of the two). `--reap-every` needs `--loop`.
- **Recipe jobs.** A process may declare `recipes` (NAME → `{resource, machines, split, piece, join, verify, prepare?, pieceTimeout?, timeout?, attempts?}`; each step an argv list, never `sh -c`; unknown keys refused with their path). `govern slice <lane> <recipe> [--machines N] [--estimate HOURS] [--bg]` runs it as one ordinary job (jobs, wait, log, kill, ledger and desk see it): `prepare` (local), `up` of the resource's machines under a tag, `split` (local; prints one piece name per line: at least one, each made of letters, digits, `.` `_` `-`, no `..`, none twice), then one worker per started machine claims pieces by atomic rename (`pieces/todo` to `doing/m<index>` to `done`; the machine id is only in the piece file, never in a path) and runs `piece`; a failed piece goes back with its attempt count and the machines that tried it, and is not given again to one of those while another machine that has not tried it is idle; it is `failed` after `attempts` (default 2); `pieceTimeout` kills the piece's whole process group; then `join` and `verify` (both must exit 0). Placeholders: `{repo}`, `{dir}` and the others as in a command, plus `{pieces}` (the job's pieces folder), `{out}`, `{tag}`, `{piece}` and `{id}` (the machine) where the step has them; an unknown `{word}` is refused at load, naming its path, and the slice words are refused inside an `sh -c` script (read `$GOVERN_PIECES`, `$GOVERN_OUT`, `$GOVERN_TAG`, `$GOVERN_PIECE`, `$GOVERN_ID` instead, which every step also gets). `down` of the tag always runs, after success, failure, a refused piece list, timeout or a stop; if it fails the job fails and `govern reap` lists the tag. Machine time is booked by `down` only; the job's ledger line has the pieces done/failed, machines and tag and no cost of its own. The allowance reserves machines x `--estimate` (else the recipe's `timeout`; a `--bg` slice needs one) before anything starts and is refused whole; `--machines` above `maxMachines` is refused, and a dedicated resource refuses other lanes. `govern desk` shows a running slice as pieces done/total and machines up. The slice has a time bound, foreground or bg: the recipe's `timeout`, else `--estimate` hours, else 30 minutes; at that time the pieces are stopped, `join` and `verify` are not run, `down` is, and the job exits 124. `govern kill` or a cap stop sends SIGTERM to the runner alone and gives it 120 s per machine plus 60 s before SIGKILL, so the `down` can finish. An unclean end (down failed, runner killed, job lost, timeout or abort without a clean down) charges the allowance at least the whole reservation, or elapsed x machines if larger, once; a late `down` does not charge again. A SIGKILLed runner leaves its pieces running until `govern kill`/`wait`, and the tag for `govern reap`. govern does not pick providers, move work between resources or keep machines warm; the piece runner holds no model.
- **Allowances.** `govern.config.json` may declare `"allowances": [...]` (or a path; `GOVERN_ALLOWANCES` names another file): `name`, `consumer` (`lane:<slug or folder/>` or `profile:<name>`), `unit` (`model-usd`, `machine-hours`, or `money` with `currency`), `limit`, optional `period` (`total`, the default, or `day`, UTC), optional `owner` (the decision owner, default `owner`) and, for model-usd, `taskEstimate`. Before a machine job on a resource or a queued task starts, govern reserves its estimate under `<state>/allowances` (one guard, all-or-nothing across allowances); at the end it releases the unused part and records the actual (task: the run's `total_cost_usd`, else tokens priced by `prices.json`; absent or invalid token usage is unknown and charged as reserved, while explicit zero usage costs zero. Input and output counters must be finite non-negative numbers; optional cache counters default to zero only when absent and must fit within total input; job: the ledger's machine seconds and money). The estimate of a job is `--estimate HOURS`, else the command's `--timeout`, else the 30-minute default limit (a `--bg` job with none is refused); a task's is `govern task send --estimate-usd N` but never below the allowance's `taskEstimate` (a floor), else `taskEstimate`, else it is refused. A reservation is a cap: a job is stopped at the seconds it reserved (min of that and its `--timeout`, `--bg` too; its log and result say "stopped at its reserved estimate"), and a sealed claude task with a model-usd reservation runs with `--max-budget-usd <reserved>`. A negative or non-finite amount is refused (reserve) or read as unknown and charged as reserved (settle). Over the allowance, a job is refused (exit 1) and a queued task stays open with a `held:` line and one BLOCKED notice to the owner; both print what was asked, what is left and who decides. Only the owner lifts it: `govern allow <name> --extra N --quote "<their own words>"` (a terminal or a live session; never Codex); the quote must contain N as a number (10 matches 10 and 10.0, not 100) and one quote grants once per allowance and period. Within the allowance nobody is asked. A reservation whose holder died is swept by the next attempt and charged as reserved. `govern desk` and `govern usage` show used, reserved and left (a bad allowance config shows as one "allowances: config error" line). Unmetered by design: a job with no resource (local) and a queued task with no lane and no profile. A lane with a money allowance whose job runs on a resource priced in another currency is refused (it names both currencies), never run unmetered. A crash between recording a charge and dropping its reservation can charge twice, which errs high.
- **Stopping a job.** `govern kill <slug> [<job>]` stops the lane's latest running job (or the one named), and the job reads `killed`. A job's processes are its own process and its descendants, for a `--bg` job every process in its process group, and, where `/proc` shows process environments (Linux), every process whose environment carries the job's `GOVERN_JOB_DIR` (every process the job starts inherits it, so one that double-forks out of the tree or moves to its own group with `setsid` is still found, also after the job's own process has exited). Limit: a process that leaves the job's tree and group and also drops `GOVERN_JOB_DIR` from its environment (or any process that leaves them, where there is no `/proc`) escapes. The job's own pid is signalled only while its start time says it is still that job: a job that ended long ago may have left its pid to an unrelated process. A stop never signals the govern doing it or that govern's parents, so a job that runs `govern kill` on its own lane does not kill the command it ran from. A stopped job reads `running` until its last process is gone; one that then turns out to have exited on its own (an exit code under 128) reads by that code instead. `<job>` is a job id, a unique prefix of one, or a command name (that command's newest job). A job's end goes into the ledger once, by whichever govern sees it end first: the foreground `govern run` (or check) that ran it, or a `govern wait` or `govern kill` on it; a `--bg` job nobody waits on or kills has only its start in the ledger. Never `kill` a job's pid by hand.
- **Advance.** `govern advance <slug>` runs the stage's check and moves on only if it passes, no owner gate holds the stage and no lane it waits on is behind. A stage with no check needs `--note "<evidence>"`; the ledger's advance entry records whether the check or the note passed the stage, and the note's words. A stage marked `"requires": "check"` (dev's test stage) passes only on a check: with none set, advance refuses a note and names the `govern check <slug> --set <cmd>` to run. `govern work <slug> <later stage>` holds every skipped stage to the same rules and refuses otherwise; going back to rework a stage is always allowed. Never edit govern.json to skip a stage.
- **Dependencies.** `govern dep <slug> --after <lane>[:<stage>]`. `govern status` and the desk show each lane as ready or blocked, and on what. A dependency that would close a cycle is refused. A finished lane shows `finished` with its stage number, never `active <stage>`. `status`, `desk` and `brief` print `⚠ stage may be behind: 34 jobs, 12 notes since the last advance 26 h ago` for a lane that is not finished, has 20 or more jobs, notes and asks since its last `advance` and no advance in 24 h: advance it (or `govern note` why not) so its recorded stage matches the work.
- **Stop hook.** `govern hook stop` runs as a Claude Code Stop hook. While this session's lane has a failing check, it refuses the stop with Claude Code's JSON block decision (`{"decision":"block","reason":…}` on stdout, exit 0), the reason naming the failure and the next command (at most 3 times per work segment). Fix the cause, don't argue with the hook. It closes nothing; the `govern hook session-end` SessionEnd hook closes a segment the session-start hook opened.
- **Runners.** The queue's `config.json` can add runners beside codex, claude and grok (`"runners": {NAME: {"argv": [...], "format": "text"|"json-result"}}`) and caps a thread at `maxRuns` (default 4), after which it goes to the owner as BLOCKED. `concurrency` (`{RUNNER-OR-PROFILE: N}`) is the most runs of that runner or profile at once across all dispatchers, counted from live claims (default 1 per runner; a message over it stays open, and a name that is no runner or profile is refused), and `maxTimeoutSec` (default 7200) is the longest `task send --timeout` may ask. The file is parsed strictly: optional `name` is a string, `maxRuns`, `maxTimeoutSec` and each `concurrency` value are positive integers, each runner's `argv` is a non-empty array of strings and its optional `format` is `text` or `json-result`; `checks` uses the content-check declarations below. Unknown keys and wrong types are refused with the file and JSON path before any message is claimed. `govern desk` keeps rendering and shows one `queue: config error` line with the file, path and message.
- One run's limit: `--timeout S` on `task send` is used instead of `GOVERN_QUEUE_TIMEOUT_SEC` and is refused above `maxTimeoutSec`; `task show` prints it. `govern task dispatch --parallel N` (and `install-service --parallel N`) runs up to N messages at once, never more than a runner's `concurrency`.
- Failed tasks: `govern task triage [--all] [--project P] [--to X] [--json]` lists `failed/` newest first with the cause (dispatcher error, parse failure, dead claim, expired, held), tokens, cost and the kept reply. After fixing the cause, `govern task retry <id> --note "<what was fixed>"` files a new open message from a failed or closed one, threaded to it, preserving its checks, verification command and verification status. A retried unverified reply is still refused by the dispatcher; its rejected content is withheld from runner prompts. Never automatic; a third retry of one original is refused.
- **Capabilities and profiles.** A capability is one grant (name, how it is called, Claude permission patterns, the Codex equivalent or "not available on codex", a side-effect class `read|write|spend|publish|push`, an optional resource and cost basis, secret NAMES only, never values). A profile is capabilities plus an engine and model. `govern caps` lists both, `govern caps <profile>` shows one's patterns, Codex mapping, classes and secret names. Built-ins ship with govern (`tools/govern/capabilities/*.json`: read, edit, web, gh-read; profiles claude-read, claude-write, codex-read, codex-write, grok-read, grok-write, researcher); a workspace adds its own in a `capabilities/` folder (a capability may not reuse a built-in's name; a profile may) (`GOVERN_CAPABILITIES`, else `govern.config.json` `"capabilities"`, else beside `projects`). `--to claude|codex|grok` is the profile `claude-read`/`claude-write`/`codex-read`/`codex-write`/`grok-read`/`grok-write` and `--write` picks the write one. A queued run is sealed to its profile: `--allowedTools` from its patterns, `--tools` with exactly the built-in tools they name and `--disallowedTools` for every other built-in (the prompt goes on stdin), `--setting-sources ""` and `--strict-mcp-config` (only the profile's own `--mcp-config`) for Claude; the sandbox and `-c` settings, and a private `CODEX_HOME` (`GOVERN_CODEX_HOME`, default `<state>/codex-home`, mode 700: a link to the real `auth.json` and a minimal `config.toml`, no project trust, MCP servers or instructions) for Codex, which is sealed except for `AGENTS.md` files under the cwd (`govern caps` says what remains on every codex profile). Grok (`grok --prompt-file … --output-format streaming-messages-json`, reading only the last result line’s `result` string; no `--json-schema`, because measured read probes passed 6/6 without it versus 4/6 with it and 3/6 with a stricter prompt; both task variants passed 6/6. The schema stays in the prompt and replies still pass `parseReply` and the reply check) gets `--tools` with exactly the profile's tools, `--permission-mode dontAsk` (`acceptEdits` where it may edit), scoped allows (`Edit(./**)`, `Write(./**)`), denies (`MCPTool(*)`, `Read(**/auth.json)`, and edits to `.grok`, `.mcp.json`, `.claude`, `.cursor`), `--max-turns` (`GOVERN_GROK_MAX_TURNS`, default 25), a private empty `HOME` and a private govern-owned `GROK_HOME` (`GOVERN_GROK_HOME`; it holds a link to the real login and a minimal config) with the Claude and Cursor compatibility layers set to 0. Grok has no dollar cap, only the turn limit and the dispatch timeout (`GOVERN_QUEUE_TIMEOUT_SEC`), which `task show` and `desk` print as `bound: N turns · T s`; a run whose spend is unknown (timeout, error, incomplete usage) is recorded without usage and settles as reserved. It is not fully sealed: project-level config under the cwd, built-in agents, bundled skills and web tools still load (`govern caps` says so on every grok profile). Grok profiles carry only read and edit: other capabilities are refused at load, because the `Bash(...)` allow syntax was not verified. The task records its profile (`task show`, `desk`). A profile holding a spend, publish or push capability runs only for a task tied to a lane (`--lane`, else the project) whose gate of that name is approved; send and dispatch both refuse otherwise and name the gate. `--lane` must be the message's project or that lane's parent. An allow pattern that can run `git push`, `npm publish`, `claude`, `codex` and the like (list: `GUARDED_COMMANDS` in lib/caps.ts) must be declared with the matching guarded effect, or the capabilities file is rejected at load. A queue config runner with the same name as a profile shadows it and runs unsealed (`govern caps` warns). `task send` refuses (exit 4) a message to a profile with no `write` capability whose summary or body asks for file changes (an edit verb within six words of file, test, module, function, branch, commit, `.ts`, `.py` or `.md`); `--write` or `--profile <write profile>` fixes it, `--read-only` sends it and records `readOnlyConfirmed`. A reply is never checked by that rule.
- **Grant self-test.** `govern caps --check <profile>` runs one probe per capability in a sealed session (model haiku, `GOVERN_CAPS_CHECK_MODEL` to change), each answered as strict JSON `{capability, status: ok|refused|error, evidence}`; govern verifies the answer (a random nonce, a file it reads itself) and an unparseable or unverified reply is a failed check. A probe may carry `expectCmd` (an argv govern runs itself, 30 s limit): its output must appear in the reply, and a failing command is an `error`. For a Claude profile the check also runs one negative probe, asking for a capability the profile lacks and whose tools no held capability already grants (when there is none the record says `negative: none applicable`, never a leak); it passes on any reply that does not claim success (a refusal, or an error such as "tool not available") when no trace of the work is found, and a reply that says it worked (or the file it asked for existing) is `leaked`. A capability without a probe is `untested`: it fails the check of a profile whose self-test is required, and `govern caps` shows it as UNTESTED. The result is recorded in `<queue>/checks/<profile>.json` with the profile's content hash. No profile runs unchecked, not even the six legacy ones: for a message whose profile has no passing check of its current definition the dispatcher runs `caps --check` itself, once per profile hash (a lock under `<queue>/checks/`), then runs or holds the message. A failed check leaves the message open with a `held:` line naming the failed capability and the command to re-run, and sends the sender one BLOCKED notice; a later message on the same failed hash is refused without re-running. `govern caps --check --all` checks every profile without a current passing check; `govern caps` shows `not run`, `stale (profile changed)` and `failed` apart. `selfTest: "optional"` now only lets a capability with no probe pass the check.
- govern improves itself this way: its own work runs as the `ops/govern` lane on the `dev` process, with the govern test suite as the test check.

## The loop

The owner says what to change. Then:

1. **Read narrowly.** Open only the file the change touches, and only the part you need (grep, offset or limit). Don't re-read what is already in this conversation.
2. **Edit the source.** Edit what generates a file, never the generated file.
3. **Build without waiting in the model.** Run `govern run <slug> <command> --bg`, then `govern wait <slug>`.
   - In Claude Code, run the wait as one Bash call with `run_in_background: true`. You are notified when it ends, and no tokens are spent while it runs. Never write sleep or poll loops, and never check a job repeatedly.
   - `wait` blocks at most 540 s (`--timeout S` changes it) and exits 124 if the job is still running then; wait again, the job runs on. When the job ends it prints the exit code, the new files and the last 12 log lines. Use `govern log <slug> --grep RE` only if those lines don't explain a failure.
   - `govern jobs <slug>` lists the lane's latest jobs (status, exit code, seconds), for when you need a job id or an older result.
4. **Show the result.** Give the owner the path to open. Read an image yourself only when you must judge it: it stays in the context for the rest of the session. State what you measured and what you could not judge.
5. **Record the decision** as soon as it is made, in one line: `govern note <slug> "chose the second supplier file; first had no totals"`. The next session starts from these notes, not from this chat.

Keep replies short: what changed, what to look at, and the open question. No long reports or tables unless asked.

## Steps that go to Codex

A step is a prompt: a markdown file with a front matter (`schema`, `rules`, `effort`, `model`, `repairs` and `description`; `repairs` defaults to 1, `description` is the line `govern prompts` shows, and any other key, a line that is not `key: value`, or a front matter with no closing `---` line is refused before Codex is called; LF and CRLF files read the same) that a process names in its `prompts` folder (or the workspace's config names in `prompts`). It runs as one verified Codex call, not as chat work in this session: `govern ask <slug> <step> [--file F]… [--var K=V]…`. `govern prompts [<process>]` lists the steps, with the file that wins for each (and the processes it serves). A prompt in the workspace's prompts folder overrides a process's prompt of the same name (the workspace wins); `ask` and `prompts` resolve it the same way. With no workspace, only the built-in processes' prompts are listed. `schema:` is required and names a JSON schema; `rules:` optionally names a JSON array of house rules, both relative to the prompt file. Every object schema (`type: "object"` or one with `properties`) must set `additionalProperties` to `false` or a schema that validates extra fields; absent or `true` is refused at any depth before a model call. For house rules, a rule is `{at, message, <one test>}`, `at` a path (`items[].text`, `[]` walks an array, `at` may be a list), the tests `forbid` and `require` (a regular expression, with `flags`), `maxWords`, `maxItems`, `minItems`, `equals`, `indexOf` (the value must index the array at that path), `minSecondsApart` (each time the path matches, `m:ss` or `h:mm:ss`, comes at least that many seconds after the one before; a value that is not such a time fails), an optional `when: {kind}`, `optional: true`, and a message that may use `{at}`, `{n}` and `{match}`. A rule whose `at` matches nothing fails, naming the rule and the path, unless it is `optional: true`. `flags` belongs to `forbid`/`require` only, and a path other than the `a.b[].c` form (for example `a[0][1]`) is rejected when the rules load. The step's `govern manual <process>` says which steps its work has.

- Output is JSON, checked against a schema and the house rules, with one automatic repair.
- Exit 3 means it failed verification. Say so; don't patch the output by hand and present it as verified.
- Present the result in a few lines, and give the owner the JSON path for the full text.
- Images can be added with `--image sheet.png`.
- The ledger's `ask` entry records what was sent: `promptSha` (sha256 of the rendered prompt, the first call's stdin byte for byte), `callShas` (every call's stdin, a repair included) and `schemaSha` (sha256 of the schema file codex was given; always present).

## Asking another agent: the task queue

Stored message JSON is parsed strictly: unknown fields and wrong types are refused with exit 4, naming the file and JSON path; invalid JSON names the file. Queue listing skips a file moved by another dispatcher between listing and reading it.

Do not message other sessions, and do not start subagents. Put the request in the queue:

```bash
govern task send --to codex|claude|grok|<runner>|<profile>|auto|owner|<session> --project <slug> --task <name> --kind TASK --summary "…" --body "…" --file <repo-relative path> [--profile <name>] [--lane <slug>]
```

- `govern task dispatch`, or the timer `govern task dispatch --loop`, starts one fresh headless session per message: `codex exec`, `claude -p` (Sonnet) or `grok --prompt-file`. The session gets only the message, its thread and the named files. Claude receives the queue-reply schema through `--json-schema`; govern reads `structured_output` from the CLI result and still checks it with `parseReply`. It never wraps another JSON shape into an envelope. The reply is verified JSON (ACK, REVIEW, HANDOFF, BLOCKED…) and is filed back to the sender. A reply that fails JSON parsing or the reply schema becomes a BLOCKED notice from the dispatcher to the sender (to the owner when the sender is a runner). The notice names the failure and the file holding the whole reply (`whole reply: …`); it never includes the raw reply text, so later runner prompts cannot inherit it. Read the kept file instead of re-running the task. `govern task install-service [--interval 30]` writes a user systemd service that runs the loop across sessions and reboots, and prints the `systemctl --user` line that enables it. Host setup includes this service as a standard step: run that install command and its printed enable command on each host. `--system` previews `/etc/systemd/system/govern-dispatch.service` with `User=` set to the current user and `WantedBy=multi-user.target`; `--system --write` writes it only as root. Without root it prints the refusal and complete unit, never escalates. PATH and GOVERN_REPO values with spaces are quoted in both units.
- Replies can carry a content check: a command run against the reply text (summary and body) right after the session ends, before the reply is filed. It is selected by the kind of the task you sent and by the kind the reply claims, and both checks run, so a reply cannot opt out by claiming another kind. For each kind, first wins: the profile's capabilities file (`check`, applied to HANDOFF, REVIEW and DECISION only, so it never runs on an ACK or BLOCKED), the queue's `config.json` (`checks`, keyed by any message kind, `TASK` included), or built in (REVIEW: every cited file reference must exist in the repo, symlinks resolved, forms `path:12`, `path:L12`, `path#L12`, `path line 12`; `checks/file-refs.ts`). It proves the cited lines exist, not that the claim made about them is true. Shape: `{"argv": ["cmd", "{reply}", "{dir}"], "timeout": 60, "label": "urls resolve"}`; placeholders `{reply}` (the reply text file), `{dir}` (the task's working dir), `{repo}`, `{node}`, `{govern}`. Exit 0 marks the reply `[checked: <label> (N)]` (N: a leading number in the check's output); anything else, including a missing binary, a timeout, a kill, an empty body on a content kind, or a checker that crashes ("could not run: <reason>"; the reply is still sent), marks it `[unverified]` (content kept; `govern task show` gives the reason and the log under `queue/replychecks/`); kinds with no check show `[shape only]`. `govern desk` counts unverified replies. Do not act on an unverified reply without reading it yourself.
- You can choose checks yourself. `--check NAME` (repeatable) adds a check to the reply: `file-refs`, `commit-refs`, `claims-cited` (send the ledger `{"claims": [{"id": "C1", …}]}` with `--file`; every id must appear in the reply), or a name the profile's capabilities file (`checks`) or the queue's `config.json` (`checks.named`) defines; an unknown NAME is refused (exit 2) and all must pass for `[checked]`. HANDOFF replies are always checked: every commit they name must exist in the project's git repository. `--verify -- <argv…>` has govern run that command (no shell, 600 s, in the project folder) after the other checks: only exit 0 gives `[checked: verify (exit 0)]`, so "tests pass" is verified by govern, not by the worker's word.
- When a finished run's reply does not parse, govern makes one repair call (same engine and profile, `read` only, cheapest model, 120 s) that must wrap the same content, then checks it like any reply; `govern task show` says "envelope repaired by one <engine> call", `task list` shows `[repaired]`. If that fails too the task fails and both texts are kept (`<id>.reply.txt`, `<id>.repair.txt`). `GOVERN_QUEUE_REPAIR=0` turns it off (`GOVERN_QUEUE_REPAIR_EFFORT`, default `low`, sets Codex's effort for it). `govern desk` counts the day's replies: checked, shape only, unverified, repaired.
- Nothing runs while the queue waits. Read replies with `govern task list --to <you>` and `govern task show <id>`, once, when the owner asks or the work needs them, not in a loop.
- `--to` must be a runner (`codex`, `claude`, `grok`, or a runner the queue's `config.json` names), a profile other than the six legacy ones (for example `researcher`), `auto`, `owner`, a configured mailbox or the name of a live Claude Code session (`~/.claude/sessions`). The legacy profile names (`claude-read`, `claude-write`, `codex-read`, `codex-write`, `grok-read`, `grok-write`) are not recipients: send to the engine, with `--write` for the write one. An unknown or dead name fails and lists the valid ones. **Sessions are not woken by the queue** (the dispatcher runs only runners and profiles): after sending to one, also tell it `govern task show <id>` with SendMessage.
- Your own mail: `govern task inbox` (open messages for you; `--all` adds closed). Answer with `govern task reply <id> --kind ACK|REVIEW|HANDOFF|... --summary … --body …` (files the reply to the sender and closes the original), `govern task close <id> --note …` when nothing needs saying, `govern task forward <id> --to <name>` when it went to the wrong name. Your name is `GOVERN_AS`, else found from your process tree; pass `--as NAME` if neither works. `govern task inbox --hook` prints a short block only when mail waits, for a UserPromptSubmit/SessionStart hook.
- Mail retention: on every dispatch tick, old local mail to a recipient that is no runner/profile, live registered agent (including aliases), live session or mailbox moves to `failed/`. Workspace config keys `mailTtlHours` (positive integer, default 72) and `mailboxes` (string array, default empty) set retention and durable inboxes; `owner` is always a mailbox. Remote `NAME@PEER` mail is left to the relay. Govern records `closedBy: "govern"` and the expiry reason; the center shows the handler and reason. A NOTICE goes to a still-known sender; dead senders get none, preventing notice loops.
- Abandoned queue runs: every claimer records its name, pid and process start time. Dispatch first moves dead claims to `failed/`, charges unknown spend as reserved and sends one BLOCKED notice to the sender (owner when the sender is a runner). It never retries them automatically: files or external effects may already have changed. `govern desk` identifies dead and unknown holders instead of counting them as running. A claim without an identity is automatically failed by govern after twice the task's limit (`GOVERN_QUEUE_TIMEOUT_SEC`, or its `--timeout`), never less than one hour, using its recorded claim time or the claimed file’s metadata-change time (ctime, updated by the claim rename) when none is recorded. Its recorded reason is "no holder recorded; claimed more than N s ago; its effects are unknown". Younger claims stay claimed. You can also inspect effects and run `govern task reclaim <id> --note "<what you checked>" [--as NAME]`. This records your name and note, applies the same failure, charge and notice path, and refuses a live holder.
- The sender is you: `--from` defaults to your session's name (as for `--as`), so replies come back to your inbox. Never send as `owner`. The owner has no inbox; anything that needs him goes to him directly in the conversation, at once.
- Prefer `--to codex` for checks: in a pilot, the same fact-check took 56k tokens and 29 s on Codex, against 122k tokens, 67 s and $0.83 on `claude -p`.
- `--write` lets the runner change files in the project folder. Default is read-only. `--profile <name>` picks another profile of the engine instead (not with `--write`: the profile decides what may change); `--to <profile>` addresses a profile directly (for example `researcher`).

## The owner's gates

- **Approvals** come only from the owner's own words. Record them verbatim: `govern approve <slug> <gate> --quote "<exactly what the owner said>"`. Never infer an approval, and never approve for the owner. **What govern checks.** Inside a Claude Code session the quote must appear (case, spacing and typographic quotes ignored; a part of a message is enough) in a message the person typed in this session's transcript, not in tool output, a file, pasted content, a reminder, or another session's or a task's message. If it is not found, `approve` fails (exit 1) and says where it looked; do not rephrase until it passes: ask the person. The approval records the session and message (`source`) in govern.json and the ledger. From a plain terminal, nothing is in a transcript to check, so the approval is recorded as typed by the OS user. A Codex or Grok session is refused (govern cannot verify it; for Grok that includes any process whose parent chain is a grok process): the person approves from their own terminal or a Claude session. A gate whose process names an `owner` other than "owner" (say `editor`) needs `--by editor`, and the approval records whose words they were. **What this does not guarantee:** it raises the bar from "any string" to "words in the person's own turn". It is not tamper-proof: an agent that can edit transcript files or the session registry can forge a typed message, and an old message that happens to contain the quote still matches. The check is a guard against your own mistakes, not a licence to approve for the person. Accepting a change to a check (`govern check <slug> <stage> --accept --quote "…"`) is checked the same way and records its `source` in the ledger.
- **The owner sees complete drafts,** not intermediate passes.
- **Publish.** `govern publish <slug>` is specific to video on YouTube: it is for a lane of a process with the gates `final` and `publish`. It refuses (exit 4) a lane whose process lacks either gate, and otherwise unless both gates are approved, the lane names the files `vpkg` (the package) and `release` (the release manifest), the package lies directly in the config's `packages` folder, and its sha256 is listed in a `channel-vpkg-SHA256SUMS-*.txt` file there. It then prints the publishing commands: a plan, then the apply, both run on the publishing host. Run those printed commands through Bash, unchanged, so a publish guard sees them. Only do this after the owner's go in this session.

## Never, in production work

- No subagents, Agent tool or Workflow. One session works one lane. An engine or tool bug goes to its owner as a queue request, not to an agent cascade.
- No messages to other sessions. State lives in `govern.json`, and `govern status` answers "where is it".
- No heavy work on the machine the owner works on: builds and renders run where the lane's commands say.
- No long logs or whole files pasted into the chat.
- No overwriting an approved file. Write the new one beside it with a suffix.

## Keep the context small

- Every govern command warns when this session reads more than 150k tokens per call. `govern ctx` shows the number.
- Context is the session's own job; never ask the owner to `/clear` or restart. When it warns:
  1. Record what is open with `govern note` (or memory), so nothing depends on the chat.
  2. Offload model work to Codex with `govern task send --to codex`, and wait on jobs in the background.
  3. Let auto-compaction shrink the rest. The dispatcher runs `govern tune` hourly, and it sets the compaction window.
- One session covers one lane and one stage at a time. For another lane, run `govern done <slug>` and start a fresh session.
- `govern work <slug> <stage> --open [--engine claude|codex|grok]`, from a terminal, starts a fresh interactive session for one lane; the child gets none of the other engines' markers, so the segment it registers records its own engine.

## Measure

`govern usage [<slug>] [--since YYYY-MM-DD]` shows, per work segment:
- calls;
- input-side tokens;
- output tokens;
- average and maximum context per call;
- cache share;
- the owner's turns, and tokens per owner message;
- `~usd` (where priced);
- the Codex `ask` steps;
- Claude Code tool calls, shown when non-zero: `tools`, `repeats` (same tool and input as an earlier call in the segment), `polls` (Bash commands that invoke `sleep` with an operand, by any path, as a command of their own: at the start, after `;`, `&&`, `||`, `|`, `&`, `(`, `{`, a newline or `then`/`do`/`else`, inside `$( … )` or backquotes, after `env`, `nice`, `timeout`, `time`, `command`, `exec` or `nohup`, or in a `bash -c`/`sh -c` script; `sleep` as an argument or inside quotes, such as `grep sleep` or `echo "sleep 5"`, is not a poll, and neither is `govern wait`), `agents` (Agent or Task spawns) and `big reads` (a Read with no offset or limit that returned over 40,000 characters).

It compares these with the chat baseline the workspace's config gives under `baseline` (omitted when there is none). Report it when the owner asks, or when a lane is delivered.

Tokens are attributed to a lane by where the session works, not by a command you remember: calls outside any segment go to the lane by `GOVERN_LANE`, then by the session's folder (the lane's folder or below, or a folder its `govern.json` names under `{repo}`), then by a queue run's project. They show as an `unsegmented · by cwd` row, counted in the TOTAL. `govern usage` with no slug and `govern desk` end with UNATTRIBUTED: today's sessions that belong to no lane, and lanes with work recorded and no session.

### Decisions (Jev, shadow mode)

*Extension: decide; `govern ext enable decide`.*

`govern decide ask --questions <file.json> (--state <text> | --state-file <file>) [--purpose P] [--json]` asks Jev (TypeSafe System One, `POST /v1/systemone`) the questions about the state and prints the answers:
- question types: `choice` (criteria: a key → description map), `score` (criteria: an ordered list of at least 2 levels), `noul` (a probability; criteria optional). Each needs `instructions`.
- the key is `TYPESAFE_API_KEY`, else the dotenv file named by `decide.envFile` in the workspace config (only that variable is read). It goes to the child process through the environment, never argv, and is redacted from errors.
- state plus the longest question must fit in 32k tokens, estimated high (an ASCII character as half a token, any other character as one); a larger state is refused before anything is sent.
- replies must answer exactly the questions asked. Only `model`, `answers` and optional `usage` are accepted at the top level; answer fields are limited to `type`, `choice`, `score`, `confidence`, `probabilities`, `legend` and `noul`. Choice and score probabilities must be non-empty, with keys from the choice criteria or score indices `"0"` through `"n-1"`; the score level comes from the highest supplied probability. Unknown fields or invalid values refuse the reply.
- every answer or failure is appended to `<queue>/decisions.jsonl` with the state's sha256 and length, never the state text or the key. Usage is recorded when supplied (about $0.042 per million input tokens): `input_tokens` and `output_tokens` must be finite, non-negative numbers. Missing usage or token counts are omitted as unknown, never recorded as zero.

With `"decide": {"shadow": true}` in the config, every TASK sent with `govern task send` is also asked `kind` (choice), `difficulty` (score) and `success` (noul). The task is clipped to fit (marked `…(clipped: N more characters)`) and TypeSafe gets 5 seconds, with 5 more for the request process to exit. Shadow mode only records: it never routes or blocks a send, delays it by at most about 10 seconds, and any failure is one `govern: decide (shadow): …` line on stderr.

`govern decide report` scores the recorded predictions against the ledger: a task succeeded when it ran with `ok` and a verification other than `unverified`. Each task counts once (its latest answer). It prints Brier and ECE (10 bins) per noul question, the count and success rate per choice, and, per score bucket, the count, success rate, money and seconds. Use it to decide whether Jev's answers are worth acting on before anything routes by them.

## Environment

govern reads these variables; the MANPAGE (`govern --help`) gives each one's default.
- Workspace: `GOVERN_REPO`, and the path overrides listed under **The workspace** (`GOVERN_PROJECTS`, `GOVERN_QUEUE`, `GOVERN_PROCESSES`, `GOVERN_WORKFLOW`, `GOVERN_PROMPTS`, `GOVERN_TUNING_LOG`, `GOVERN_CAPABILITIES`, `GOVERN_RESOURCES`, `GOVERN_ALLOWANCES`, `GOVERN_STATE`).
- Sessions: `GOVERN_AS` (your queue name), `GOVERN_SESSIONS_DIR` (the Claude Code session registry), `GOVERN_CLAUDE_PROJECTS`, `GOVERN_CODEX_SESSIONS` and `GOVERN_GROK_SESSIONS` (where `govern usage` finds transcripts), `GOVERN_CLAUDE_SETTINGS` (the settings file `govern tune` writes), `GOVERN_GROK_HOME`.
- Programs: `GOVERN_CODEX_BIN`, `GOVERN_CLAUDE_BIN`, `GOVERN_GROK_BIN`, `GOVERN_PYTHON` (fills `{python}`).
- Limits and models: `GOVERN_CTX_WARN` (the context warning), `GOVERN_TARGET_CTX` (what `govern tune` aims at), `GOVERN_MAX_INLINE` (file text `govern ask` inlines), `GOVERN_QUEUE_MAX_INLINE` (file text a queued message inlines), `GOVERN_QUEUE_TIMEOUT_SEC` (one dispatched run; default 900 s), which a message's `--timeout` replaces for that run; the holderless-claim bound is twice the run's limit, at least 3600 s, `GOVERN_QUEUE_REPAIR` (`0` turns the envelope repair off) and `GOVERN_QUEUE_REPAIR_EFFORT` (Codex effort for it, default `low`), `GOVERN_QUEUE_CLAUDE_MODEL`, `GOVERN_QUEUE_CODEX_EFFORT`, `GOVERN_QUEUE_GROK_MODEL`, `GOVERN_GROK_MAX_TURNS`, `GOVERN_CAPS_CHECK_MODEL`, `GOVERN_GROK_CHECK_MODEL`, `GOVERN_JEV_MODEL`, `GOVERN_TYPESAFE_URL`.
- The webhook (extension business): `GOVERN_WEBHOOK_TOKEN`, the bearer token `govern event-listen` requires.
- Extensions: `GOVERN_EXTENSIONS`, the comma-separated names of the extensions to enable, instead of the config's `extensions` (empty is unset).
- Tests and diagnosis: `GOVERN_NOW` (the allowances clock), `GOVERN_PROC=ps` (read the process table with ps).
- Set by govern for what it runs, never by you: `GOVERN_JOB_ID` and `GOVERN_JOB_DIR` (every job), `GOVERN_TAG`, `GOVERN_LANE`, `GOVERN_RESOURCE`, `GOVERN_COUNT` and `GOVERN_ID` (a resource's commands), `GOVERN_PIECES`, `GOVERN_OUT` and `GOVERN_PIECE` (a slice's steps), `GOVERN_REPLY_FILE` and `GOVERN_TASK_FILES` (a reply check: the reply text, and the task's attached files as a JSON array), `GOVERN_CONVERSATION_RUN` (a conversation worker; an approval from under it is refused).

## Business processes

*Extension: business; `govern ext enable business`.*

See [BUSINESS.md](BUSINESS.md) for typed case data, conditional graph routes, parallel joins, assigned human tasks, and quorum approval policies. Use `govern data` to prepare fields and `govern advance <slug> --stage <stage>` to complete a specific active branch. Use `govern human` to list, claim, delegate, or complete stage tasks and `govern human-inbox` for tasks assigned or claimable by the current human. Use `govern reject` to record a policy veto and follow its declared rework route. Human task decisions and policy votes require the mapped human OS account and verified human words; never impersonate people or infer approvals. Policy votes expire and are invalidated by changed case data. Existing linear processes retain their behavior.

## Durable lifecycle

*Extension: business; `govern ext enable business`.*

See [LIFECYCLE.md](LIFECYCLE.md) for timers, business calendars, events, recovery, subprocesses and process revisions. `govern tick` emits due reminders and escalation alerts; `govern alerts` lists or acknowledges them. `govern event` delivers a stable, correlated event id; `govern event-listen` is the authenticated loopback webhook adapter. `govern subprocess` starts or syncs a declared child and never treats an unfinished child as success. `govern recover` requires verified human words before retrying exhausted checks or resolving uncertain compensation. `govern process pin` freezes an existing lane; `govern process migrate` requires a higher revision, explicit mappings where needed and the human's own quoted migration decision. Never infer that an external effect was undone: inspect compensation results before confirming them.

See [Loops and dynamic branching](ITERATION.md) for bounded repeats, conditional fan-out, typed collections, and per-item subprocess joins.

## Persistent conversations

*Extension: conversation; `govern ext enable conversation`.*

Govern owns conversation history separately from case state; see [CONVERSATIONS.md](CONVERSATIONS.md). Use `govern conversation create <id> --profile codex-read` (or a trusted configured `--adapter`) and optionally `--lane` to bind a case. `govern conversation list`, `govern conversation show <id>` and `govern conversation history <id>` read the durable records. Submit with `govern conversation send <id> --message "..." --request-id KEY`; `--mode interrupt` requests cancellation before a replacement turn. `--message-file` reads UTF-8 input. Submission queues work; `--run` executes it, and `--run --bg` survives this caller disconnecting.

`govern conversation run <id>` drains queued turns serially and streams NDJSON progress. `--once` executes at most one; `--bg` starts a detached worker. A second worker cannot write an active session. Codex profiles use the queue's private `CODEX_HOME` seal (`GOVERN_CODEX_HOME`, else `<state>/codex-home`, login and minimal config only) and sync refreshed authentication back after the run. `govern conversation events <id> --after N` replays persisted events; `--follow --timeout 30` streams them for a bounded interval. Partial assistant output and tool progress are provisional. Only an explicit successful provider result, exit 0 and any declared profile output check can commit an assistant reply. Committing transport-valid prose does not establish its factual accuracy or advance a case.

`govern conversation cancel <id> <run-id> --reason "..."` preserves partial work and requests process-group shutdown. It does not undo external effects. A worker crash leaves an interrupted run and blocks further execution. Inspect those effects, then use `govern conversation recover <id> --action continue|retry|cancel --note "..."`; retry is an explicit new attempt. Conversation state is not a human approval source: model processes cannot approve business gates, and existing case checks and human-source rules still apply.

Context is bounded and never silently truncated. `govern conversation context <id> --summary "..." --through <completed-assistant-message-id>` checkpoints completed history while retaining original messages and events. Summaries are historical context, not authority. `govern conversation close <id>` closes an idle session; history remains readable. Conversation state lives under the workspace's state folder and must be retained for restart. Never edit its JSON directly.

## Extensions

Peer, center, remote, decide, conversation and business are extensions: a workspace enables each one it uses, and the others are not loaded. A fresh workspace enables none.

- `govern ext list` shows every extension with its state, its size in bytes and its commands. `govern ext enable <name>` and `govern ext disable <name>` write `extensions` in `.govern/config.json`; in a workspace with a `govern.config.json` that file is the owner's, so they are refused (exit 4) and name the file to edit by hand. `GOVERN_EXTENSIONS` (comma-separated) replaces the file's list. Enabling is workspace setup: nothing is ledgered.
- The commands: peer owns `peer`, `mesh` and `agents`; center owns `center`; remote owns `remote`; decide owns `decide`; conversation owns `conversation`; business owns `event`, `event-listen`, `tick`, `alerts`, `subprocess`, `recover`, `human`, `human-inbox`, `data` and `reject`. The rest of the commands are the core's.
- A command of a disabled extension prints one line, `govern: <command> is part of the <name> extension, which this workspace does not enable — govern ext enable <name>`, and exits 4. `govern task send --to NAME@PEER` is refused the same way while peer is off, and `govern task dispatch --loop` relays to peers and renews the mesh only while it is on.
- `govern help` lists the core commands and one `extensions:` line with each extension's state. `govern help <command>` of an enabled extension prints the command's lines and rules, then the extension's own manpage text. `govern help --topics` lists an extension's documents only while it is enabled, each marked `(extension: <name>)`; `govern manual --size` prints a third line for them.
- `govern desk` and `govern status` never load a disabled extension and do not fail because of an enabled one: peer adds a line with its peers and the messages waiting for them, and remote one with its paired devices, when there is something to show.
